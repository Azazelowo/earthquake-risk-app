# 門檻通知

> 日期：2026-11-21。分兩個階段：**階段 A 已實作**（不需要任何伺服器）；**階段 B 只有設計**（伺服器推播，沒有實作、沒有建立任何帳號或部署）。
> **只寫實際讀到、跑過的**；沒有查證到的標「待查」。

## 1. 範圍與不做的事

| 做 | 不做 |
|---|---|
| 規則掛在「我的情境」上：狀態升到某個倍數、機率達到某個值、附近有新的地震報告 | **地震預警／EEW／震波倒數**：沒有即時波形，做了也比官方慢，而且會讓人誤以為這是預警 |
| 在 APP 開著、資料更新時評估，用瀏覽器的 Notification API 在手機上送出 | 轉發第三方即時警報資料：專案先前查證 ExpTech 條款為「讓使用者直接連 API、不要經自己的伺服器轉發；TREM 資料不可用於預測」（`AGENTS.md`），所以通知**只用我們自己的 feed**，不使用 ExpTech 的地震列表 |
| 通知文案中性、附「平常」當對照、固定寫「不是預報／預警」 | 「安全」「保證」「即將發生」這類字眼 |

## 2. 平台限制（本次實際讀到的）

| 項目 | 查到的內容 | 來源（讀取日 2026-11-21） |
|---|---|---|
| iPhone／iPad 的網頁通知 | iOS／iPadOS **16.4** 起，**加入主畫面的網頁 App** 才支援 Web Push；要求通知權限必須是回應使用者的直接操作（例如按「訂閱」按鈕）；通知可與專注模式整合，使用者可逐 App 管理；Web Push 用 Apple 的推播服務（APNs），**不需要加入 Apple Developer Program** | WebKit 官方部落格〈Web Push for Web Apps on iOS and iPadOS〉`webkit.org/blog/13878/` |
| Periodic Background Sync（讓 service worker 在 APP 沒開時定期醒來） | MDN 標為**實驗性技術**；在 Chrome，這項權限**只給已安裝並以獨立應用程式開啟過的網頁 App**，而且 Chrome 依網站的互動分數決定會不會、多久觸發一次；最小間隔只是請求值，使用者代理可能依其他因素調整 | MDN〈Web Periodic Background Synchronization API〉 |
| Android Chrome、桌面 Chrome／Firefox／Safari 的通知行為 | **沒有逐一查證**（待查：到各瀏覽器的官方文件或 MDN 相容性表確認，並在真機測試） | — |

**所以階段 A 的設計是**：只在使用者按按鈕時要求權限（iOS 的明確要求；其他瀏覽器沿用同一做法）；iPhone 沒加入主畫面時畫面上只顯示「先加入主畫面」；**不依賴 Periodic Background Sync**（實驗性、只有 Chrome、不保證觸發）。

## 3. 階段 A：行為（`src/notify/`）

| 規則 | 條件 |
|---|---|
| 狀態升到某個等級（`level`） | 倍數（模型 ÷ 平常）≥ 1.5、3 或 10（和首頁狀態用同一組門檻 `LEVEL_EDGES`）。預設選 3 倍 |
| 機率達到某個值（`prob`） | 機率 ≥ 使用者設的值（0.01%–90%），可選「且倍數至少 R」 |
| 附近有新的地震報告（`quake`） | feed 的 `recent` 出現震央在情境範圍內（全台情境＝整個網格）、ML ≥ 門檻、最近 24 小時內的**新**事件 |

通用規則：

- **邊緣觸發**：只在「從未達標變成達標」那一刻通知一次。達標後要降到門檻的 **85%** 以下才算回到未達標（避免在門檻上下抖動一直通知）。
- **cooldown**：同一條 `level`／`prob` 規則至少相隔 6 小時（`quake` 規則每個事件本來就不同，不受限）。
- **第一次只記下現況**：剛建立規則時，已經達標的條件和 feed 裡已經存在的地震**不會**馬上通知。重新啟用規則視同新建立。
- **寧可不通知**：假資料、資料發布超過 2 小時、模型沒涵蓋這個位置、算不出倍數、情境已刪除，一律不通知；而且這些情況**不改變規則狀態**（資料恢復後不會因為「看起來剛達標」而誤通知，也不會漏掉真正的變化）。
- **送不出去不算通知過**：沒有權限或送出失敗時，狀態退回通知前，之後權限好了還能通知。
- 倍數小於 1 **不會觸發**等級規則；設定畫面顯示實際倍數（首頁的 `ratioText` 會把 <1.15 都寫成「約 1 倍」），並寫明「比近兩年平均安靜」不是「比較安全」。
- 規則、狀態、位置都只存在這支手機（localStorage），刪除情境時掛在它上面的規則一併清掉。

### 預設門檻的依據

`src/format.ts` 的 `LEVEL_BACKTEST`（破專題 `app/state_frequency.py`，測試期 2015-01-01～2026-09-30、20 個縣市代表點、首頁預設條件 50 km・3 天・M5 以上）：

| 倍數 | 占所有「縣市×天」的比例 | 每個縣市每年約幾天 |
|---|---|---|
| ≥ 1.5 | 約 8.3%（0.0743＋0.008＋0.0002） | 約 30 天 |
| ≥ 3 | 約 0.8%（0.008＋0.0002） | 約 3 天 |

所以預設 3 倍；選 1.5 倍通知會很頻繁。這只是首頁預設條件的數字，其他條件沒有算過。

## 4. 階段 A：驗證與已知限制

- **單元測試**：`src/notify/notify.test.ts`，30 個。我另外做了變異測試：拿掉回彈區間、拿掉「第一次只記下現況」、讓 blocked 重置狀態，各會讓對應的測試失敗。
- **瀏覽器實測**（`vite preview`，真實的 feed）：新增三種規則、壞輸入被拒絕並說明、情境名稱的 HTML 被跳脫、設定畫面顯示每條規則「現在的倍數與是否達門檻」。
- **沒有驗證的**：
  - **沒有在真的手機上看過通知**。內嵌瀏覽器的通知權限是「封鎖」，所以**通知本身有沒有跳出來、點了會不會回到 APP，都沒有實測**（`showNotice`、`notificationclick` 只有程式碼）。
  - iOS 加入主畫面後的流程、Android Chrome 的行為：待查／待真機測試。
  - APP 完全關閉時不會通知：這是階段 A 的設計限制，不是缺陷。

## 5. 階段 B 設計：伺服器推播（**只有設計，沒有實作**）

**為什麼需要**：階段 A 在 APP 關閉時完全不通知。要做到「手機鎖著也通知」，只能由伺服器發 Web Push。

### 5.1 需要的元件

| 元件 | 做什麼 |
|---|---|
| VAPID 金鑰對 | 伺服器證明「這則推播是我發的」。**私鑰是祕密，不能進 git** |
| 訂閱端點的儲存 | 使用者允許後，瀏覽器給一個端點（URL＋金鑰）；伺服器要存起來才能發 |
| 規則的儲存 | 伺服器要知道每個訂閱者的條件（情境的位置、半徑、門檻）才能評估 |
| 評估與發送 | 每次 feed 更新（每 15 分鐘）後，對每個訂閱者評估規則並發送 |
| service worker 的 `push` 事件 | 收到推播時顯示通知（目前只有 `notificationclick`） |

### 5.2 隱私影響（要先決定）

階段 A 的最大優點是**位置完全不離開手機**。階段 B 要讓伺服器評估規則，就必須把**位置（至少是降精度後的座標）與規則傳到伺服器**，並存放訂閱端點。這會改變 APP 目前「沒有帳號、不上傳位置」的承諾（資訊頁「位置與隱私」），**必須在介面上明確告知並讓使用者同意**。一種折衷：伺服器只存「網格格子編號＋門檻」，不存座標，把降精度做在手機端；是否可接受，由使用者決定。

### 5.3 方案比較

| | A. Cloudflare Worker＋KV＋Cron | B. GitHub Actions 發送 |
|---|---|---|
| 做法 | Worker 提供訂閱 API（寫入 KV），Cron Trigger 每 15 分鐘讀 feed、評估、發 Web Push | 沿用 `hourly-feed` 工作流程，產生 feed 之後多一步發送 |
| 訂閱儲存 | KV | 需要另一個儲存（repo 檔案不適合放使用者的訂閱端點；公開 repo 會洩漏） |
| 已查到的免費額度（Workers Free） | 每日 100,000 次請求；每次 CPU 10 ms；每次最多 50 個外部子請求；每個帳號 5 個 Cron Trigger；KV 每日 100,000 次讀、**1,000 次寫**、1 GB（來源：Cloudflare 官方文件〈Limits〉〈KV pricing〉，2026-11-21 讀取） | **待查**：GitHub Actions 的免費額度與排程可靠度（本專案實測 GitHub 內建排程會延遲數小時，目前靠外部服務呼叫 `workflow_dispatch`） |
| 風險 | **每次最多 50 個外部子請求**：訂閱者超過 50 人時，一次 Cron 發不完，要分批或升級付費；KV 每日 1,000 次寫入也是上限（訂閱與規則異動每次都寫）；10 ms CPU 對加密簽章是否足夠**待查**（Web Push 需要 ECDH／簽章運算） | 訂閱端點放哪裡是根本問題 |
| 需要使用者做的事 | 註冊 Cloudflare、建立 Worker 與 KV、設定 VAPID 私鑰為 Worker secret | 同上，另需儲存服務 |

**我的傾向**（推測，非定論）：若使用者決定做階段 B，方案 A 較合理；但訂閱者人數若會超過幾十人，免費額度就不夠，要先評估付費（Workers Paid 的價格本次沒有查）。對 12/9 的展示，階段 A 已經足夠展示「規則與通知」的完整流程。

### 5.4 iOS 的限制

依第 2 節：只有加入主畫面的網頁 App 才能收 Web Push，iOS 16.4 起；一般 Safari 分頁沒有（Apple 這篇文章沒有談到分頁，所以只能說「文章沒說有」，未驗證）。
